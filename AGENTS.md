# This is NOT the Next.js you know

# Meero

Browser platform: describe a web application in natural language → AI generates a real, **secure, production-ready, FULL-STACK Next.js (App Router) + TypeScript + Tailwind + shadcn/ui web app** whose entire backend is the **user's own linked Supabase project** — real Postgres tables with RLS, real Supabase Auth end-user sessions — running live in the browser. Users connect their Supabase account via OAuth; every Meero project is bound to one of their Supabase projects, and every build applies its generated `schema.sql` to that project's real database via the Supabase Management API. **Every generated app carries a required, mechanically-guaranteed "Created by Meero" badge** (owner decision, 2026-07-25: the badge is validated at codegen time AND injected as a static fallback by the build worker if somehow missing — never optional, never removable by the generated code). Generated apps were rebuilt from vanilla HTML/CSS/TypeScript to real Next.js + shadcn/ui the same day, also per owner decision — don't reintroduce the old `index.html`/`styles.css`/`main.ts` shape. The **Pro and Ultra plans unlock a one-click production release** — a real Vercel deployment (actual REST API, Vercel running its own `next build`, real public URL). Connecting GitHub **immediately creates the project's repo** and then **commits every successful build — and every auto-fix — straight to `main`** (owner decision, 2026-07-28: builds commit to main directly, a clean linear trace superseding the earlier per-build-PR flow; only runtime self-heal fixes are intended to arrive as a reviewable PR). Every generated app also ships a **required runtime error reporter** (a mechanically-guaranteed file, like the badge) that writes real production errors into a `_meero_runtime_errors` table on the user's own Supabase; the orchestrator reads them back via the Management API to power **autonomous production self-healing** (surface real errors in the builder → one-click fix through the normal pipeline). This supersedes the brief client-only/localStorage web-app iteration, which superseded generative-3D-scenes, which superseded the AI-app-builder / Expo-vs-native product and a considered-and-rejected AI-PCB pivot. Product renamed from "Zylo" to **Meero** on 2026-07-21; every identifier, Redis key namespace, and Stripe metadata key uses `meero`. Full product spec and milestone status live in `README.md`.

**Marketplace (owner decision, 2026-07-21)**: every project has `projects.is_public` (`00015_marketplace.sql`). **Free-plan projects are ALWAYS public** — enforced by the `projects_enforce_free_public` trigger, which forces `is_public := true` on insert/update whenever the owner's plan is `free`, regardless of which client is writing (this is a product rule, not a privileged-column bypass concern, so unlike the billing/GitHub/Supabase triggers it applies to every role, not just non-service-role callers). Pro/Ultra default to private and get a normal user-settable toggle (`VisibilityToggle` → `setProjectVisibility()` in `apps/web/src/app/projects/actions.ts`). Public projects (and their `builds`/`specs` rows) are readable by any authenticated user via additive RLS policies — `build_files`/`build_artifacts` deliberately get NO public policy, since **cloning** goes through `POST /projects/{id}/clone` (service role, bypasses RLS). A clone is re-pointed at the **CLONER'S own Supabase** (the request carries `supabase_project_ref`, validated against their real Management API project list): it copies the source build's `build_files` (placeholder source — nothing of the original owner's backend leaks), links the new project, and enqueues a **bundle-only** web-queue job (`use_build_files: true` — codegen skipped, schema applied to the cloner's database, a real `next build`), charging a flat `CLONE_COST`. That charge is a credit sink on the cloner, NOT a payout to the original creator — real creator payouts are the not-yet-built "crypto transactions" direction the owner has floated; don't fake or stub a payment rail for it before it's real.

## Absolute rules (do not violate)

- Every build produces the SAME thing: a real, secure, full-stack **Next.js (App Router) + TypeScript + Tailwind + shadcn/ui** application — `package.json`, `next.config.mjs`, `tsconfig.json`, `tailwind.config.ts`, `postcss.config.mjs`, `app/globals.css`, `app/layout.tsx`, `app/page.tsx`, `components/meero-badge.tsx`, `components/ui/*.tsx`, `lib/utils.ts`, `lib/supabase.ts`, `schema.sql` (the required-file manifest lives in `_REQUIRED_FILES` in `app/agent/codegen.py`) — with the user's own Supabase as the entire backend. There is no per-plan framework choice — `build.platform` is always `'web'`. NEVER generate a raw HTML/CSS/vanilla-JS project, Vue/Three.js/React Native/mobile code, or server code — those belonged to prior products or don't exist in this architecture. Generated code may import ONLY the vendored toolchain — `next`/`react`/`react-dom` (+ `/*` subpaths), `@radix-ui/*`, `lucide-react`, `class-variance-authority`, `clsx`, `tailwind-merge`, `tailwindcss-animate`, `tailwindcss`, `postcss`, `autoprefixer`, `@supabase/supabase-js`, plus local modules via `@/` or relative paths (`ALLOWED_PACKAGES`/`ALLOWED_PACKAGE_PREFIXES` in `app/agent/codegen.py`) — enforced by `_validate_bundle()`'s import scan, and nothing else is vendored on the build worker anyway. (`tailwindcss`/`postcss`/`autoprefixer` were missing from this allowlist for a window on 2026-07-25 despite being vendored — every generated app's own `tailwind.config.ts` failed codegen until fixed; if a "vendored" package still fails validation, check this list is actually in sync with `VENDORED_PACKAGE_VERSIONS`.)
- **package.json dependency versions are mechanically pinned** — `VENDORED_PACKAGE_VERSIONS` in `app/agent/codegen.py` is the single source of truth (mirrored as a literal table in `app/agent/prompts.py`'s `_SHARED_CODEGEN_RULES`, and installed with matching version ranges in `apps/orchestrator/Dockerfile`'s vendor stage — **keep all three in sync** whenever a version changes). `_validate_bundle()` parses the generated `package.json` and hard-fails codegen if it declares a package outside that set or a version string that doesn't match exactly. This matters because the local build worker ignores `package.json` entirely (it symlinks the pre-installed `node_modules` directly, never runs `npm install`), but a real Vercel release DOES run `npm install` from it — so its resolved dependency tree must match what was actually built and tested locally, or a release could succeed/fail differently than the preview that supposedly represents it.
- **Every generated app carries a required, mechanically-guaranteed "Created by Meero" badge.** `components/meero-badge.tsx` must exist and contain the `data-meero-badge` marker; `app/layout.tsx` must render `<MeeroBadge />` — both checked by `_validate_bundle()` before codegen can succeed. As a belt-and-suspenders backstop, `web_worker.py`'s `_ensure_badge()` inspects every actual built HTML page and injects a static (inline-styled, Tailwind-independent) fallback badge if the marker is somehow still absent. Never let generated code hide, remove, or conditionally skip the badge.
- **Generated apps are secure by construction, enforced mechanically** — `FORBIDDEN_MARKERS` in `app/agent/codegen.py` hard-fails codegen on any XSS/injection sink (`dangerouslySetInnerHTML` — caught via the `innerHTML` substring match — plus `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval(`, `new Function`, `javascript:`) and any raw network marker (`fetch(`, `XMLHttpRequest`, `WebSocket(`, `http(s)://` — W3C XML-namespace strings excused for inline SVG). ALL remote I/O goes through supabase-js; the Supabase URL/anon key enter generated code ONLY as the `__SUPABASE_URL__`/`__SUPABASE_ANON_KEY__`/`__SUPABASE_WS_URL__` placeholders (validated present), and the serving path ONLY as `__BASE_PATH__` (validated present in `next.config.mjs`) — all substituted by the web/deploy worker per build. **RLS is the generated app's real authorization boundary** (the anon key is public by design): `_validate_schema_sql()` allowlists `schema.sql` statement-by-statement (idempotent `create table/index if not exists`, `alter table … enable row level security / add column if not exists`, `drop policy if exists`, `create policy` — NO drops/truncate/grants/roles/functions/extensions) and rejects any created table that doesn't enable RLS with ≥1 policy. Functions/triggers (including the classic Supabase "auto-create a profile row on signup" trigger) are banned with NO exception, `security definer` or not — this was previously enforced but undocumented in the prompt itself, which meant codegen kept reaching for a signup trigger, failing validation, and the auto-fix retry hitting the identical wall with no guidance on the alternative (fixed 2026-07-25). `_SHARED_CODEGEN_RULES` in `app/agent/prompts.py` now explicitly states the real alternative: create any needed per-user row from the CLIENT right after `supabase.auth.signUp()` succeeds, under the new user's own session — `auth.uid()` already equals their id then, so it's covered by a normal owner-scoped policy with no elevated privilege ever needed. If a future schema.sql rejection loops through auto-fix without resolving, check whether the prompt gives a concrete alternative for whatever it's being rejected for, not just the ban itself. `_validate_schema_sql()` also catches two `create policy` shapes that used to only fail once applied to the user's REAL Postgres — a multi-verb `FOR` clause (`for insert, update ...`, a straight Postgres syntax error; each verb needs its own `create policy`) and a USING/WITH CHECK clause naming a column the table doesn't have (e.g. checking `auth.uid() = user_id` on a `profiles` table keyed straight on `auth.users` via `id`, which has no `user_id` column) — both were previously only caught by the live SQL apply, producing a cryptic `42601`/`42703` Postgres error that auto-fix would loop on without a named alternative to fix toward (fixed 2026-08-02). `_SHARED_CODEGEN_RULES` now spells out the exact USING/WITH CHECK pairing per verb and the "check the column that's actually declared" rule, mirroring the same "ban + concrete alternative" pattern as the signup-trigger fix above. React's automatic JSX escaping (never `dangerouslySetInnerHTML`) is the XSS boundary — this is why the CSP had to relax to `script-src 'self' 'unsafe-inline'` (Next's static export embeds an inline hydration payload React itself needs); `connect-src` still stays locked to the linked Supabase project. Don't weaken any of this to "make codegen pass more often" — the auto-fix path exists for that. `_validate_bundle()` also dedicates a check (outside `FORBIDDEN_MARKERS`, so it can give a named alternative like the signup-trigger/policy-shape fixes above) to any `next/font` import — it fetches font files over the network at `next build` time, and the build worker runs the real build fully offline against a pre-vendored toolchain with no install/fetch step, so it would otherwise silently break the build instead of failing validation up front (fixed 2026-08-09, alongside the UI-quality pass below).
- **UI quality is prompted for explicitly, not left implicit** (2026-08-09): `_SHARED_CODEGEN_RULES` in `app/agent/prompts.py` carries a dedicated "visual design is a hard requirement" section — named anti-patterns (untouched shadcn slate palette, cookie-cutter navbar+hero+3-cards+footer, no hover/focus states) are called a failed generation exactly like a build error, then given concrete direction: a full HSL design-token set (primary/accent/gradient/shadow tokens) in `app/globals.css` mapped into `tailwind.config.ts`, never a bare `text-white`/`bg-black` in a component; typography via Tailwind's built-in `font-sans`/`font-serif` stacks plus scale/weight contrast (no custom font files — see the `next/font` ban above); visual interest via CSS gradients/patterns/icon compositions instead of stock photography, since generated apps can neither fetch external images nor generate them; real hover/focus/loading/empty states everywhere interactive. `AppPlan.design`'s field description was tightened to match (a specific domain-appropriate palette, not "clean and modern") so the planning stage commits to an executable theme before codegen starts.
- NEVER mock, fake, stub, or simulate any pipeline stage — every build applies `schema.sql` to the user's REAL database (Supabase Management API `POST /v1/projects/{ref}/database/query`), runs a real `next build` (static export), generated-app sessions are real Supabase Auth sessions, a Pro/Ultra release goes through Vercel's real REST API with Vercel running its own real `next build` (polled until READY), and GitHub PRs are real PRs. UI must report true state (e.g. "No app yet", "Link Supabase to build"), never placeholder/simulated output.
- **Supabase connect** (`app/supabase_connect.py`, `00017_byo_supabase.sql`): `supabase_connections` holds real Management API OAuth access+refresh tokens and gets **zero** RLS policies for `authenticated`/`anon` — service-role only, exactly like `github_connections`. `profiles.supabase_connected` and `projects.supabase_project_ref/supabase_url/supabase_anon_key` are the non-secret projections the UI reads, trigger-protected (`protect_supabase_connected()` / `protect_supabase_link_fields()`) — never write these from the web app; the orchestrator writes them only after real Management API calls confirmed them (`POST /projects/{id}/supabase/link` validates the ref against the user's actual project list). `fresh_access_token()` auto-refreshes expired tokens and re-persists them. Linking (and cloning) calls `disable_email_confirm()` (best-effort) so generated-app signups work instantly — a documented v1 product decision. Builds are gated on a linked project at three layers: `POST /builds`, the chat agent (`graph.py` appends an honest "link Supabase first" note instead of queueing a doomed build), and the web worker itself. **Connecting is auto-provisioning, not picking** (owner decision, 2026-08-08, `00045_supabase_auto_provision.sql`): once the OAuth callback saves the connection, `_start_supabase_auto_provision()` (`app/main.py`) picks the user's first real Supabase organization and calls the real Management API to create a brand-new project — connecting the account is the only step, no more choosing from a list of existing ones. Real provisioning takes on the order of a minute, so the ref isn't written to `projects.supabase_project_ref` (which every build/chat gate already treats as "ready") until it's genuinely active — `supabase_provisioning_status`/`_ref`/`_error`/`_started_at` (same trigger-protected pattern as the 00017 link fields) track the in-flight state, and the in-process `_start_supabase_provision_poller` (same shape as the email poller/runtime monitor) polls real project status until ACTIVE, then reads the anon key and calls `db.set_project_supabase_link()` to finalize — or marks it `failed` on a terminal Management API status or `supabase_provision_timeout_s`. The old manual picker (`POST /projects/{id}/supabase/link`, still listing the user's real existing projects) stays wired up as the fallback the builder offers if auto-provisioning fails, and as the explicit picker the marketplace clone flow (`POST /projects/{id}/clone`) still uses on purpose, since a clone needs to re-point at a SPECIFIC existing project, not a fresh one.
- **The live app pipeline** (`app/workers/web_worker.py`, any plain Linux host — heavier CPU/RAM than the old esbuild-only pipeline since it runs a real `next build`): materializes source (from the codegen archive, or from the build's own `build_files` rows for bundle-only clone jobs), applies `schema.sql` to the linked Supabase FIRST (a SQL failure is a genuine build failure fed to auto-fix), substitutes the `__SUPABASE_*__`/`__BASE_PATH__` placeholders (workspace copy only — stored `build_files` and GitHub pushes keep portable placeholder source; `__BASE_PATH__` → `/preview/{build_id}` for live previews), symlinks the **pre-vendored** Next/React/Tailwind/shadcn/Supabase toolchain (`Settings.app_vendor_dir`, installed once at image-build time — no `npm install` ever runs per build), runs `node_modules/.bin/next build` with `NEXT_TELEMETRY_DISABLED=1` (no network calls at build time either), then walks the produced `out/` directory and uploads EVERY file (not a fixed 3-file list — Next's own `_next/static/...` asset tree included) to the `previews` bucket, running `_ensure_badge()` on each HTML file first — but `builds.preview_url` is NEVER Storage's own public object URL; it's the orchestrator's own `GET /preview/{build_id}/{path}` proxy (`app/main.py`). Confirmed by direct testing: Supabase Storage unconditionally forces `text/html` to `text/plain` and adds a blocking CSP to every publicly served object, so the app could never execute from the Storage URL — the proxy re-serves with real headers. After success the worker calls `maybe_open_build_pr()` (best-effort, never fails the build). Phase events: `generating_code`/`fixing_code` → `applying_schema` → `building_app` (mapped client-side to the `"bundling"` UI phase).
- **Production release** (`app/workers/deploy_worker.py`, separate explicit action per build via `POST /builds/{id}/deploy` — NEVER automatic, NEVER part of the base pipeline): ships the build's real generated Next.js SOURCE (read from `build_files`, substituted for the linked Supabase project with `__BASE_PATH__` → `""` since a release serves from its own domain root) through Vercel's real REST API (`POST /v13/deployments`, inline base64 files, `target: "production"`, `projectSettings.framework: "nextjs"` so Vercel installs the pinned dependencies and runs its OWN real `next build` — never the already-built preview bundle; polled until READY; one stable Vercel project name per Meero project via `vercel_project_name()`). Gated on `Settings.vercel_configured` and `profile.plan in ("pro", "ultra")` (Pro & Ultra — NOT free); charged `DEPLOY_COST` separately from `WEB_BUILD_COST`. Success persists via `db.set_build_deployment()` → `builds.deploy_url` + `projects.live_url` (trigger-protected, `00016_web_pivot.sql`) + a `'deployment'` artifact; progress streams as `build.deploy_phase` WS events. A failed release never changes `builds.status`.
- Every table gets RLS policies BEFORE any data is written — no exceptions. (This applies to Meero's own schema AND, via `_validate_schema_sql()`, to every table a generated app creates on the user's Supabase.)
- A feature is "done" only when a real signed-up Supabase Auth user can use it end to end.

## Stack (locked)

- Frontend: Next.js 16 App Router + TypeScript + Tailwind v4 (this repo)
- Auth: Supabase Auth via `@supabase/ssr` cookie pattern — clients in `apps/web/src/lib/supabase/` (browser `client.ts`, server `server.ts`, session refresh `proxy.ts` wired through `apps/web/src/proxy.ts` — Next 16 renamed middleware to proxy)
- DB: Supabase Postgres; schema + RLS in `supabase/migrations/`; row types in `apps/web/src/lib/types.ts`
- Orchestrator (in `apps/orchestrator/`): Python FastAPI + Redis queues (`app/queues.py`) + WebSocket status (`app/main.py`); codegen + chat agent use **LangChain/LangGraph over two model providers, dispatched by plan** (`app/agent/codegen.py`, `app/agent/graph.py`) — free-plan users stay on OpenAI's cheap model (`openai_model_free`); Pro/Ultra get **Claude Sonnet via Anthropic** (`anthropic_model`, owner decision, 2026-08-09, superseding the original all-OpenAI choice from 2026-07-16). `model_for_plan()` is the ONLY place plan→model routing lives; `llm()` dispatches `ChatOpenAI` vs `ChatAnthropic` purely by whether the resolved model name starts with `"claude"`, so every call site (chat replies, structured codegen calls) stays provider-agnostic — both populate LangChain's standard `usage_metadata` for token billing, but `stream_usage=True` is OpenAI-only (Anthropic includes usage in streaming natively) and Anthropic's Messages API requires an explicit `max_tokens` on every call (defaulted to 8192 where a call site doesn't pass one), unlike OpenAI. Workers: `app/workers/codegen_worker.py` (any host — plans the app, generates the full Next.js project, enqueues to the web queue), `web_worker.py` (plain Linux host — schema→Supabase, placeholder substitution, a real `next build` (static export) against the vendored toolchain → uploads the whole `out/` tree to the `previews` bucket → `/preview` proxy → best-effort GitHub PR), `deploy_worker.py` (plain Linux host with outbound HTTPS — Pro/Ultra real Vercel release, Vercel building the real Next.js source itself). Billed via Stripe (`/billing/*` in `app/main.py`).

## Conventions

- **Production domain is meero.im / api.meero.im, switched by ONE flag** (owner decision, 2026-07-25 — meero.im was purchased that day). `apps/orchestrator/app/config.py`'s `Settings.app_env` (`local`/`prod`, from `APP_ENV` in `apps/orchestrator/.env`) drives `_derive_env_urls()`, a `model_validator` that fills in `frontend_url`/`public_base_url`/`allowed_origins`/`github_oauth_redirect_uri`/`supabase_oauth_redirect_uri`/`billing_success_url`/`billing_cancel_url`/`billing_portal_return_url` with the real `https://meero.im`/`https://api.meero.im` values (or localhost) — but ONLY when that specific field is left blank in `.env`; an explicit value always wins regardless of `app_env`, so a one-off override (e.g. a staging domain) still works. When adding a NEW config field that's environment-dependent, follow this pattern (blank default + a line in `_derive_env_urls()`) rather than hardcoding a localhost default that someone has to remember to change later. The one thing this can't reach: Next.js inlines `NEXT_PUBLIC_ORCHESTRATOR_URL` into the client bundle at **build time**, so switching it needs a different Docker image, not a runtime toggle — `docker-compose.prod.yml` (a separate `APP_ENV=prod` in the root `.env`, read by the `Makefile`) layers that one build-arg override on top of `docker-compose.yml`. Going to prod also requires updating the GitHub OAuth App's and Supabase OAuth App's own callback URLs, and the Supabase project's Auth Site URL, by hand in their respective external dashboards — `APP_ENV` cannot reach those. See README.md §12 for the full checklist.
- Server actions live in `actions.ts` files (`apps/web/src/app/(auth)/actions.ts`, `apps/web/src/app/projects/actions.ts`, `apps/web/src/app/billing/actions.ts`, `apps/web/src/app/profile/actions.ts`) and return `{ error?: string }`-style state for `useActionState`.
- `builds`/`build_artifacts`/`build_files` are user-read-only; only the orchestrator (service role) writes them. The web app never holds the service-role key. `build_files` (`00006_build_files.sql`) holds the real generated Next.js project (every file — `package.json` through `schema.sql`, placeholder form, never substituted values) per build and powers the builder's **Code** tab — written via `db.replace_build_files()` right after generation and BEFORE the build is dispatched (code-first; never build/run before the code is ready). Bundle-only clone jobs, and the deploy worker's Vercel release, also read their source back from here.
- Specs are immutable, versioned per project (`unique(project_id, version)`); chat follow-ups append the next version.
- Design tokens (white/ink palette + the `accent` orange family, `meero-gradient`, shadows) are defined in `apps/web/src/app/globals.css` via Tailwind v4 `@theme`. The UI is white everywhere; the orange/white gradient belongs to the home hero (and its soft variant to auth) — don't spread it across app surfaces.
- **Plans/credits (TOKEN-based, 2026-07-19)**: `profiles.plan` (`free`/`pro`/`ultra`), `credits_remaining`, `credits_reset_at`, `bonus_credits`, and `stripe_*` columns are trigger-protected (`protect_profile_privileged_columns()` in `00004_billing_credits.sql`, extended in `00009_credit_topups.sql`) — only the service-role client can change them. Credits are a **weekly token** budget — refreshes every Sunday at 00:00 UTC (`next_weekly_reset()` in `00012_weekly_token_reset.sql`; free 20k / pro 400k / ultra 2M per week — `plan_daily_tokens()` in `00010_token_billing.sql` still names the per-plan amount, mirrored display-only in `PLAN_CREDIT_LIMITS` in `apps/web/src/lib/types.ts`; keep in sync). Billing is **gate-then-reconcile**: `credits_available()` gates on balance `> 0` BEFORE running (no deduct), then `charge_credits()` deducts the true cost AFTER (weekly pool first, then `bonus_credits`, each floored at 0 — never negative). A **chat turn** deducts the real OpenAI `total_tokens` it consumed (captured in `app/agent/graph.py` via `stream_usage=True` + `include_raw=True`; `CHAT_MIN_CHARGE` fallback if usage is missing). An **app build** deducts a flat `WEB_BUILD_COST`. The **ultra Vercel release** deducts a separate, larger flat `DEPLOY_COST` — both in `app/config.py`. The legacy `consume_credits()` is kept but unused. One-time $5 top-up — a permanent "Buy more tokens" option in the account settings' Billing & usage tab (owner decision, 2026-08-08, replacing the earlier time-limited nav countdown banner that gave away a 5M-token grant) — adds `CREDITS_TOPUP_TOKENS` (250k, sized to actually be worth the $5 charge rather than read as an "unlimited for a week" giveaway) real bonus tokens. Free plan uses `OPENAI_MODEL_FREE`; Pro/Ultra use `OPENAI_MODEL` (`model_for_plan()` in `app/agent/codegen.py`). Never let the web app decrement credits or set plan/billing fields directly — always go through the orchestrator.
- Stripe webhook (`/billing/webhook`) is the only writer of `plan`/`stripe_subscription_*`; keep `STRIPE_PRICE_PRO`/`STRIPE_PRICE_ULTRA` in sync between Stripe and `apps/orchestrator/.env` or plan detection in the webhook breaks. The webhook branches on `checkout.session.completed`'s `mode`: `"subscription"` → plan upgrade (existing path); `"payment"` with `metadata.meero_credit_topup` set → real one-time credit top-up (`db.add_bonus_credits`), a completely separate flow from plan billing (`POST /billing/checkout-credits`, `STRIPE_PRICE_CREDITS_TOPUP`).
- `queues.publish_event()` swallows Redis connection errors by design (logs + returns) — a worker on infra that can't reach a locally-hosted Redis shouldn't crash over it, and Supabase remains the source of truth regardless. Don't "fix" this by making it raise again; if you need guaranteed delivery, put Redis behind a publicly reachable host instead.
- `Settings.openai_api_key` defaults to `""` (not required) — only add new required (no-default) fields to `Settings` if every context that imports `app.config` can supply them (e.g. `deploy_worker.py` never calls OpenAI, only `vercel_token`).
- **Auto-fix**: `builds.retry_of` (`00007_build_retry.sql`) links a build to the one it auto-fixed. Capped to one hop by convention (never chain a fix onto a fix) — enforced in `POST /builds/{id}/auto-fix` (`app/main.py`) and mirrored client-side in `BuildStatusListener`. Real second codegen call fed the actual error — `next build` OR schema-apply failure, both genuine, extracted from the real logs by `extract_build_errors()` in `app/workers/common.py` (`fix_project()` in `app/agent/codegen.py`) — then a real second run; spends a credit like any build. The fix path carries the ORIGINAL app plan forward unchanged (never re-plans) via the source archive's `metadata.plan`.
- **GitHub → commits to main** (owner decision, 2026-07-28, supersedes the earlier per-build-PR flow): `github_connections` (`00008_github_publish.sql`) holds real OAuth access tokens and gets **zero** RLS policies for `authenticated`/`anon` — not even SELECT — so it's completely inaccessible from the browser; only the service-role orchestrator (`app/github_publish.py`) ever touches it. `profiles.github_username` and `projects.github_repo_full_name`/`github_repo_url` are the non-secret projections the UI reads, trigger-protected the same way as the billing columns — never write these from the web app. **Connecting GitHub immediately creates the repo** (`ensure_project_repo()`, README-initialized so `main` exists) and links the project — there's no separate "publish" step, and the `/auth/github/callback` does it right after saving the token; the `POST /projects/{id}/github/publish` endpoint now just covers the "already connected on an earlier project, link this one too" case. After that, `maybe_commit_build_to_github()` (called by the web worker post-success, best-effort) commits each build's complete regenerated tree **straight to `main`** as ONE real commit (blobs → tree → commit → ref, no `base_tree`, so a file removed by a fresh codegen run doesn't linger), with a message distinguishing a normal build from an `Auto-fix build …`. A best-effort commit failure never fails the build. `open_pull_request()` is kept for the runtime self-heal path (a captured production error → a reviewable fix PR rather than a direct commit). Pushed source always carries the `__SUPABASE_*__` placeholders, never real values. There is a first-run **connect-on-start prompt** in the builder (`github-connect-prompt.tsx`) for owners of unlinked projects (dismissible per project via sessionStorage).
- **Autonomous self-healing / runtime error telemetry**: every generated app carries a REQUIRED, mechanically-validated client error reporter (`components/meero-error-reporter.tsx`, marker `data-meero-error-reporter`, rendered in `app/layout.tsx` — enforced by `_validate_bundle()` exactly like the badge) that writes real runtime errors (via supabase-js — generated apps can't `fetch()`) into a REQUIRED `_meero_runtime_errors` table in the user's own Supabase (enforced by `_validate_schema_sql()`; RLS with an anon+authenticated **insert-only** policy — visitors report but never read others' errors, and the orchestrator reads server-side via the Management API which bypasses RLS). Both the reporter and the table are specified verbatim in `app/agent/prompts.py`'s `_SHARED_CODEGEN_RULES`. The orchestrator reads unresolved errors via `fetch_runtime_errors()` (`app/supabase_connect.py`, missing-table-safe for apps built before this shipped) exposed at `GET /projects/{id}/runtime-errors` (+ `/resolve`); the builder's `runtime-errors-panel.tsx` surfaces them. **"Fix with Meero" is a REAL autonomous fix** (`POST /projects/{id}/runtime-errors/fix`): a genuine codegen call fed the real captured error (reusing `fix_project`'s existing `fix_of` path as-is — `codegen_worker.py` now prefers the new build's OWN `error` field, set at creation time, before falling back to the original build's stored error), then a real build. `builds.is_runtime_fix` (`00021_runtime_auto_fix.sql`) marks it — `web_worker.py` uses that one flag to ship the result as a reviewable GitHub PR (`maybe_open_runtime_fix_pr`, reusing `open_pull_request`) instead of committing straight to `main` like every other build; this is the one deliberate exception to the "builds commit to main" rule, since a runtime fix is speculative in a way a build that already passed a real compile isn't. `db.create_runtime_fix_build()` links back to the succeeded build via `retry_of` (reused generically — it already means "which build this one is meant to fix," regardless of why) but does NOT go through the compile-error `/auto-fix` endpoint's one-hop cap, since it's a different endpoint for a different trigger. "Discuss in chat" remains as a manual fallback.
- **Readiness checklist — plain-English "is my app ready?" for non-technical owners** (`app/readiness_check.py`, `builds.readiness_checks` jsonb — `00022_readiness_checks.sql`): every generated app ALSO exposes its real Supabase client on `window.__meeroSupabase` (required, marker `MEERO_WINDOW_HOOK_MARKER = "__meeroSupabase"`, enforced in `lib/supabase.ts` exactly like the badge/reporter) — this is what lets the platform drive genuine signup/login/RLS checks against the live app with a headless Chromium without knowing anything about its specific UI (no DOM/selector guessing). Right after every successful build, the web worker runs three REAL checks against that build's own `/preview` page (same internal-URL pattern as `_capture_screenshot`): (1) signup via `auth.signUp`, (2) login via `auth.signInWithPassword`, (3) **data privacy** — signs out, then does an actual anon-role `select("*").limit(1)` against every table `owner_scoped_tables()` identifies from the real `schema.sql` text as genuinely owner-scoped (its SELECT-applicable policy's `USING` clause references `auth.uid()` — deliberately NOT "any policy on this table mentions auth.uid() anywhere," since a table can be intentionally public-to-read while still having an owner-checked INSERT policy, e.g. a feedback board; flagging that would be a false "your data leaked" alarm on a table working exactly as designed). A table with no owner-scoped tables to check reports `passed: null` ("not checked yet") — NEVER a fake pass. Exposed at `GET /projects/{id}/readiness`; `readiness-checklist.tsx` renders it as a collapsible strip in the Preview tab, plain sentences only, no jargon.
- `projects.live_url` (`00016_web_pivot.sql`) mirrors the most recent real Vercel release and is trigger-protected (`protect_live_url()`) — only the orchestrator writes it, and only after Vercel genuinely reports READY. Don't set it optimistically.
- Don't reintroduce a "platform" concept on `projects` — everything about which target to build lives on `builds.platform`, which is now always `'web'` (`00016_web_pivot.sql`; historical rows may carry `'scene'`/`'ios'`/`'android'`/`'expo'`).
- **Custom domains** (Pro/Ultra, `00026_custom_domains.sql`, `app/workers/deploy_worker.py`'s `add_domain()`/`get_domain_status()`/`remove_domain()`): a real Vercel Domains API attachment, gated in `_domain_context()` (`app/main.py`) on ownership, plan, `Settings.vercel_configured`, and the project having a real prior release (`projects.live_url` set — that release is what creates the Vercel project a domain attaches to). `projects.custom_domain`/`custom_domain_verified` are trigger-protected (`protect_custom_domain_fields()`) and only ever reflect Vercel's own live verification response — `DomainManager` polls `GET /projects/{id}/domain` every 15s while unverified, never assumes.
- **Team/collaborator invites** (`00027_collaborators.sql`): `project_collaborators` links an EXISTING Meero user (resolved by email via `db.find_user_by_email()`, service-role — v1 has no pending/invited state, a row is active the moment the owner adds it via `POST /projects/{id}/collaborators`) to a project. A collaborator gets real working access — chat, builds/fixes/cancel/retry, the live WebSocket — via `db.can_access_project()` (owner OR collaborator; used in place of `is_project_owner` in those specific endpoints) and additive RLS on `projects`/`messages`/`specs`/`builds`/`build_files`, but NEVER account-level actions (GitHub/Supabase OAuth, deploy, domains, managing collaborators themselves — those stay hard-gated to `is_project_owner` directly). Every collaborator-triggered build or chat turn is billed to the **project owner's** credits (`create_builds`/`chat_stream` resolve `owner_id` from the project row, not the caller) — team-seat semantics, not a way to spend someone else's plan for free on your own account. A collaborator's builder needs the OWNER's Supabase/GitHub/plan state (whose connections the app actually runs on) without leaking the owner's `profiles` row (stripe ids, credit balances) — solved with a narrow security-definer RPC, `project_owner_public_profile()`, returning only `github_username`/`supabase_connected`/`plan`, rather than widening `profiles` RLS (which is row-level, not column-level).
- **Transactional email** (optional per-app capability, NOT a required file like the badge/error-reporter): if an app's spec genuinely needs to send mail, codegen creates a `_meero_emails` table (`MEERO_EMAILS_TABLE` in `app/agent/codegen.py`, exact shape documented in `prompts.py` — `_validate_schema_sql()` checks the required columns only when the table is actually present) and inserts a row (`to_email`/`subject`/`body`, `authenticated`-only insert policy) whenever the app wants a real send. An in-process background poller on the `api` service (`_start_email_poller`/`_poll_pending_emails` in `app/main.py`, same pattern as the stuck-build reaper — no separate worker/Docker service) scans every Supabase-linked project every `Settings.email_poll_interval_s`, reads real `status = 'pending'` rows back via the Management API (`fetch_pending_emails()`), and sends each through Resend's REST API (`app/email_send.py`), writing the true `sent`/`failed` outcome back onto the row (`mark_email_status()` — deliberately only ever touches the `status` column, never a provider-error column outside the required schema, since an `UPDATE` naming an unknown column fails the WHOLE statement in Postgres and would otherwise leave a failed send stuck on `pending` forever). `Settings.email_rate_limit_per_project_per_hour` is a real per-project cap counted from actual `status = 'sent'` rows (`count_recent_sent_emails()`), not separately tracked state — the backstop against a malicious signed-up end-user of a generated app burning its owner's Resend quota. A blank `RESEND_API_KEY` makes the poller's pass a genuine no-op; rows just stay `pending`, nothing pretends a send happened.
- **Solo mode vs. Manual mode** (`projects.autonomy_mode`, `00028_autonomy_mode.sql` — default `'solo'`, today's original behavior): in Manual mode, `apply_node` (`app/agent/graph.py`) still decides a build is ready but, instead of queueing it, parks the target spec on the trigger-protected `projects.pending_build_spec_id` and asks in chat; a real build only starts via `POST /projects/{id}/approve-build` (same create/enqueue/charge path as `POST /builds`, then clears the pointer) or gets discarded via `POST /projects/{id}/dismiss-build`. The chat UI's build-approval card and `AutonomyModeToggle` (owner-only; `autonomy_mode` itself is a plain owner-writable column, no trigger, like `is_starred`) live in `chat-panel.tsx` / `autonomy-mode-toggle.tsx`. Manual mode also suppresses the automatic AI auto-fix trigger in `build-status-listener.tsx` (which otherwise fires `POST /builds/{id}/auto-fix` the instant an eligible build fails, with zero user interaction) in favor of a real user-clicked `AutoFixButton` hitting the identical endpoint — same real second-codegen-call-plus-recompile either way, just user-triggered instead of automatic. Deploys and Supabase/GitHub connection actions were ALREADY always-explicit, separate user actions before this feature existed, so Manual mode doesn't need to (and doesn't) touch them.
